# FitSaathi — critical review (reliability, functionality, UX, overall)

Reviewed: branch `ccr-a0626cfc-6eqsx1` (6 commits, ~20k lines). Date: 2026-11-03.

Method: read the TypeScript, SQL and Kotlin sources; ran `npm run check` (ESLint 0 warnings, `tsc -b` clean,
63/63 Vitest specs); built the web bundle; drove the production build headless in Chromium through onboarding and
every tab (0 console errors, screenshots); probed edge cases with throwaway vitest scripts; three independent
sub-reviews (Android native layer, UI screens, pure logic + tests) whose findings were then verified in source.
Nothing below was changed in the code; this document is the only addition.

## Verdict

The app is a strong v1 skeleton with a clean architecture (SQLite as the single source of truth, pure unit-tested
logic, thin native plugins, versioned migrations) and an honest set of acceptance docs. It is **not** ready to hand
to a real user yet. The gaps cluster in four places:

1. **Data correctness bugs** that silently corrupt what the Progress tab reports (weekly %, projection ETA, meal
   times, midnight rollover).
2. **The notification/widget action path double-applies** when the app is open (water +500 ml per tap).
3. **The Android layer has never been compiled or run.** Reading finds no definite compile blocker, but several
   Android 13/14 behaviours (full-screen intent permission, exact-alarm permission changes, second alarm while one
   is ringing, crash loop on a bad stored alarm) will only show up on a device.
4. **UX feedback loop**: taps give no acknowledgement until the DB round-trip finishes, errors render a blank screen,
   destructive actions are bare `window.confirm`, and forms accept nonsense until submit.

Recommended order: fix the Critical and High items in sections 1–3 first (they are small, mostly one-line logic
fixes with missing tests), then compile the Android project and run `docs/ALARM_TEST.md`, then do the UX pass.

## 4. UX

What works: the daily loop is 1–2 taps, Today has everything (fasting countdown, habits, supplements, water, weight,
steps), XP bursts and the progress ring feel rewarding, empty states on Progress are well written, the design tokens
are consistent, dark mode is mostly complete, no horizontal overflow and ≥ 44 px targets held up in my checks.

What feels rough (ordered by impact):

1. **No acknowledgement on tap** until SQLite returns (see H12). This is the single biggest "feels broken" issue.
2. **Destructive actions are bare `window.confirm`** with no undo: delete habit + history (earned XP not revoked),
   erase all, forgot-PIN wipe, delete photo. `Habits.tsx:332`, `ProfileScreen.tsx:471`, `LockScreen.tsx:106`,
   `Progress.tsx:354`. → in-app modal, hold-to-confirm, archive-with-undo for habits.
3. **Skip / Miss buttons on every habit row** give the two rare actions the same weight as Done and add 12 grey
   buttons to the screen. "Miss" as a manual action is unusual (auto-miss at day end is the norm). → long-press or
   swipe for skip, drop manual miss or move it behind the row.
4. **Water habit and water tracker are disconnected**: the user must tap +250 ml twelve times _and_ tick "3L water".
   → auto-complete the water habit when the target is hit; same idea for "Dinner before 19:00" from the meal log.
5. **Water card is below the fold** on Today (after 6 habits and 3 supplements) though it is the most frequent
   action. → move water/weight quick actions to the top or into a sticky row.
6. **Mixed time formats**: Today shows "6:40 am", Habits/Profile show "19:00"/"05:30"; the fasting card says
   "Eating opens at 12:00 pm · 17:7", where "17:7" reads like a broken time rather than the IF ratio. Profile shows raw
   day codes "mon tue wed …". → one format (respect device 12/24 h), label the ratio, localise day names.
7. **Developer-facing copy in the UI**: import preview shows raw JSON paths (`fasting.eatEnd`, `habits[3l_water]`),
   hint text references `src/schema/profile.schema.json`, "Strength — Loop-style score, gentle decay". The "Profile
   JSON" card with Export/Import is the second card on Profile. → human labels, move JSON tools under Advanced.
8. **Forms validate only on submit** with schema-speak errors far from the field; numeric fields can't be cleared
   (H11). Weight field is always labelled "(kg)" even when the unit is lb while the card shows lb.
9. **Dialogs are not real dialogs**: no focus trap, no Escape, no focus return, body scroll not locked, backdrop tap
   silently discards an unsaved habit draft. Toast has no `role="status"`. `user-scalable=no` blocks pinch zoom
   (WCAG 1.4.4). No `prefers-reduced-motion` for confetti/bounce/shake. `ui.tsx:110-152,186,215`, `index.html:5`.
10. **Stale lockout message**: after the cooldown ends the pad still says "try again in 30s", and the pad shakes every
    second during cooldown because the error string changes each tick. `LockScreen.tsx:185,204`, `PinPad.tsx:116`.
11. **Settings that mislead**: the fasting-notification toggle shows off when fasting is disabled and toggling it
    persists a no-op; the "AI future look" toggle asks a scary cloud confirm for a stub. `ProfileScreen.tsx:296`,
    `Progress.tsx:231`.
12. **Food day navigation** has no "back to today"; "+ Log food" is a small header button for the most frequent
    food action. `Food.tsx:42-48`.
13. **i18n is not real yet**: ~18 hardcoded English alarm titles/bodies in `sync.ts`, plus aria labels, unit labels,
    series names, `"{n} attempts left"` with no plural form, sentence assembly by concatenation. Adding `hi.json` /
    `mr.json` as the README suggests would leave half the app in English.
14. Dark-mode gaps: legend swatches in Habits, recharts tooltip/axis defaults in Progress.

## 5. Overall / engineering

- **Per-tap cost is high.** Every action → DB write → global `revision` bump → the screen re-queries everything →
  `syncNative()` rebuilds the full alarm set (incl. 28 motivational slots with a dynamic `import()` per slot), rewrites
  the `alarms` table, and calls three native plugins. `Today`/`Habits` load **all habit logs ever** per revision and
  recompute streaks per habit per render. Progress decrypts full-size photos into data URLs for thumbnails. Fine for
  month one; will degrade over a year. → debounce `syncNative`, only rebuild motivational alarms daily, query logs for
  a bounded window, per-habit SQL aggregates, thumbnail cache.
- **No transactions around multi-step writes** (habit log + XP, meal + XP). A crash between them leaves XP
  inconsistent. → wrap in `BEGIN/COMMIT` via a `db.transaction()` helper.
- **Fail-open PIN check**: `attemptPin` returns `ok: true` if `pinHash`/`pinSalt` are missing while `appLockEnabled`
  is true (corrupted settings = no lock). `security.ts:37`. Lockout uses wall-clock `lockoutUntil`, so a clock change
  bypasses the cooldown. → fail closed; persist a monotonic attempt counter.
- **Profile JSON is stored and read back unvalidated** (`profileRepo.get` is `JSON.parse` + cast). Any future shape
  change needs a profile migration path that doesn't exist yet. `typicalMeals` arrays and the pasted JSON have no
  size caps. `slug()` collapses "Omega 3"/"omega-3" into the same supplement/habit id.
- **Bundle**: 905 kB main chunk (267 kB gzip) in a WebView — recharts, ajv and sql.js are the bulk. Lazy-load
  Progress (recharts) and the import validator (ajv) to cut cold start.
- **Spec drift**: `quotes.json` hard-codes "cricket", "05:30", "19:00" although `types.ts` promises nothing is
  hardcoded to the owner.
- **Tests look at the wrong things.** 63 specs pass, but none exercise `completionStats` with `to > today` or
  `times_per_week`, `weekly.ts` is untested, fasting never tests the wrap-past-midnight window it advertises,
  projection never tests `flat`/stale ETA, quotes "no repeats" passes trivially because 28 < 64, backup never tests
  tampered `iterations` or bad rows, streak tests never cover an explicit miss today. Component tests assert that
  services are _called_, not that the UI reflects state; they key on English strings/emoji. The native layer has zero
  tests and was never compiled. → add the regression tests for C2/H2/H3/H4/H5/H7/H8 first (they are pure functions
  and cheap), then an Android instrumentation smoke test for alarm scheduling.
- **Docs are honest and good** (`DEVIATIONS.md`, `SELF_CHECK_REPORT.md` say plainly what was not run). Keep that
  discipline; update the self-check after the first device run.

## 6. Suggested work order

1. One-line logic fixes + regression tests: C2, H2, H3, H4, H13, H5 (anchor + reached), H6 (goal direction).
2. Data-safety: C3 (strip lock keys from backup), H8/H9 (restore validation, KDF clamp, AAD), C1 + A6 (dedupe and
   atomic drain of pending actions), fail-closed PIN.
3. Screen-level fixes: C4 (reset picker), C5 (error card), H1 (midnight), H10 (unit), H11 (inputs), H12 (pending
   state + optimistic toggle).
4. Android: compile; A1–A4 before the first device test; then `docs/ALARM_TEST.md`; make reminders inexact (A5).
5. UX pass: items 2–7 in section 4, then a11y (item 9), then i18n hygiene (item 13).
6. Performance: debounce `syncNative`, bounded log queries, lazy chunks.
